# FindNearby 기존 단계 검토와 후속 개발 계획

검토일은 2026년 11월 8일이다. 요구사항 정의서와 1~6단계의 README 및 검증 기록 13개를 대조했다. 검토 착수 시점의 작업 폴더에는 프로젝트 지침을 포함한 Markdown 파일 14개가 있었으며, `Dev`와 `Build`는 비어 있었다.

재개 1~6단계에서 웹 기준본, 카카오 실연동, 추천 탐색, 지역 공공데이터와 모바일 화면을 구현하고 검증했다. 다음 작업은 [재개 7 통합 인수·성능·비용 검증](#재개-7-통합-인수성능비용-검증-기존-8단계)이다. 기존 9단계의 배포는 시험 배포와 공개 전환으로 나눠 진행한다.

## 재개 전 발견 사항과 수정 우선순위

### 우선 해결할 검증 공백

1. **실행 기준 소스가 필요하다.** README에는 `src`, `server`, 테스트, 의존성 파일과 실행 스크립트가 설명되어 있지만 현재 저장소에는 문서만 있다. 최신 6단계 원본을 확보해야 기존 구현을 이어서 수정할 수 있다. 확보가 어려우면 요구사항과 단계 기록을 바탕으로 기능을 재구현하는 분기로 진행한다. [6단계 파일 구성](Stage1To6/nearby-route-map-stage6/README.md)

2. **실제 연결 검증이 다음 단계로 계속 이월됐다.** 1단계는 실호출 통과 후 2단계로 진행하도록 정의했으나, 6단계에도 실호출과 전체 React 빌드가 미실시로 기록되어 있다. 초기 프로토타입 작업으로 활용할 수 있으며, 인수 완료 여부는 실제 실행 결과로 다시 판정해야 한다. 경로 3건의 연결 성공에 더해 지도, 시설 검색, 데이터, 이용 조건을 확인해야 한다. [1단계 판정](Stage1To6/route_api_tech_validation/TECHNICAL_VERIFICATION_REPORT.md), [6단계 한계](Stage1To6/nearby-route-map-stage6/STAGE6_VERIFICATION.md), [SRS 13절](REQUIREMENTS_DEFINITION_SRS_v1.0.md)

### 실제 데이터와 운영에서 보완할 사항

- **공중화장실과 접근점 품질**은 실제 원천 CSV와 검증된 출입구를 확보해 평가해야 한다. 6단계는 좌표 누락 행 제외, 주소 좌표 변환, 이름·350m 매칭을 구현했다고 기록한다. 주소 대표점의 오차, 동명이거나 가까운 시설의 잘못된 연결, 좌표가 없는 지역의 검색 공백을 실자료로 확인한다. [6단계 검증 4절](Stage1To6/nearby-route-map-stage6/STAGE6_VERIFICATION.md)
- **좌표와 경로 데이터 계약**을 정리해야 한다. 1단계의 `[경도, 위도]`와 이후 단계의 `{lat, lng}`는 변환 경계가 분명하면 함께 사용할 수 있다. 내부 필드와 외부 API 변환 위치를 명시하고, SRS의 경로 계산 시점 및 대중교통 도보거리도 응답 계약에 포함한다. [1단계 설계 조정](Stage1To6/route_api_tech_validation/TECHNICAL_VERIFICATION_REPORT.md), [4단계 응답 형식](Stage1To6/nearby-route-map-stage4/README.md), [SRS 9절](REQUIREMENTS_DEFINITION_SRS_v1.0.md)
- **비용 제한의 지속성**이 필요하다. 기존 분당 12회·일일 50회 제한은 프로세스 재시작으로 초기화된다. 실제 API 시도, 재시도, 상세 조회, 주소 변환을 서비스 전체 기준으로 집계하고 재시작·동시 요청에서도 한도가 유지되도록 해야 한다. 화면에서 직접 호출하는 지도·검색 API의 사용량도 제공자 지표와 함께 관리한다. [5단계 호출 제한](Stage1To6/nearby-route-map-stage5/README.md), [SRS FR-20 및 NFR-12](REQUIREMENTS_DEFINITION_SRS_v1.0.md)
- **캐시와 저장 정책**을 실데이터 수집 전에 확인해야 한다. 경로 3분 메모리 캐시와 주소 변환 JSON 캐시의 저장·재사용 조건, 출처 표시, 지도 표시 조건을 각각 확인한다. 기록상 정책 확인은 미완료다. [5단계 주의사항](Stage1To6/nearby-route-map-stage5/STAGE5_VERIFICATION.md), [6단계 운영 조건](Stage1To6/nearby-route-map-stage6/README.md)

## 공식 문서 확인 결과

2026년 11월 8일 조회한 카카오 공식 문서에서 도보와 대중교통 경로 엔드포인트, 도보 `SHORTEST` 옵션을 확인했다. 기존 API 조합을 실제 계정으로 검증할 근거가 있다. 앱별 이용 가능 여부와 실제 응답은 후속 실호출에서 확인한다. [카카오맵 REST API](https://developers.kakao.com/docs/ko/kakaomap/rest-api)

자동차 다중 목적지 API는 최대 30개 목적지, 길찾기 반경 최대 10,000m를 명시하며 응답은 거리·시간 요약을 제공한다. 따라서 20km 시설 검색과 상세 경로선에는 별도 처리가 필요하다. [카카오모빌리티 다중 목적지](https://developers.kakaomobility.com/guide/navi-api/destinations)

공개 쿼터·가격표의 도보·대중교통 각각 일 1,000건 및 초과 건당 10원, 자동차 일 10,000건 및 해당 가격 구간의 초과 건당 8원, 다중 목적지 일 1,000건 및 초과 건당 20원은 1단계 기록과 일치한다. 실제 예산은 앱별 무료 적용 여부와 설정을 확인한 뒤 산정한다. [카카오 쿼터](https://developers.kakao.com/docs/ko/getting-started/quota), [카카오모빌리티 가격](https://developers.kakaomobility.com/price/)

공공데이터포털 원천 페이지는 이번 조회에서 정상 열람되지 않았고, 카탈로그 검색 색인과 직접 조회 응답도 달랐다. 6단계의 좌표 제공 중단 설명과 현재 제공 컬럼은 공식 원천파일을 확보할 때 재확인한다. [공중화장실 데이터 페이지](https://www.data.go.kr/data/15075531/standard.do), [공식 카탈로그](https://www.data.go.kr/catalog/15075531/standard.json)

## 단계별 작업 계획

재개 1~5는 기존 1~6단계의 보완 작업이다. 이를 마친 뒤 기존 번호인 7~9단계로 이어간다. 아래 산출물과 완료 조건을 기준으로 진행 상황을 판단한다.

### 재개 1 소스 확보와 실행 기준 마련

**선행 조건은 최신 6단계 소스 또는 원본 ZIP 확보다.**

- 최신 소스, 프런트·백엔드 의존성 파일, 테스트, 환경변수 예시, 데이터 템플릿을 확인하고 `Dev`에 개발 기준본을 배치한다.
- Node·Python·라이브러리 버전과 실행 명령을 기록한다. 원본을 확보할 수 없으면 동일한 SRS를 기준으로 프로젝트 뼈대부터 재구현하고 기능별 검증을 붙인다.
- 기존 테스트, 전체 타입 검사, 프런트 빌드, 백엔드 시작, 데모 화면을 재현한다. 기록된 95건과 실제 테스트 목록의 차이를 확인한다.
- 신규 폴더에는 용도 문서를 작성한다. Agent.md의 클래스명 규칙을 적용할 대상과 함수·컴포넌트 모듈, 도구가 지정한 파일명의 처리 기준을 개발 전에 명확히 한다.

**산출물**은 실행 가능한 개발 기준본과 설치·실행·검증 기록이다. **완료 조건**은 새 환경에서 문서에 적힌 절차로 설치, 전체 빌드, 테스트, 화면과 서버 실행을 재현하는 것이다.

### 재개 2 실제 API와 데이터 이용 조건 확인

**선행 조건은 실행 기준본과 로컬 환경에 설정된 API 키·앱 권한이다.**

- 카카오 지도, 주소 검색, 편의점·역 검색, 도보·대중교통·자동차 경로와 자동차 다중 목적지 요청을 각각 확인한다.
- 정상 구간에서 거리·시간·경로 좌표·환승 정보를 검증하고, 경로 없음과 인증·쿼터·응답 형식 오류를 구분한다.
- API별 권한, 실제 적용 쿼터, 표시·캐시·저장 조건과 테스트 호출 예산을 기록한다. 조건을 충족하기 어려운 제공자는 SRS 기능을 기준으로 대체 가능성을 검토한다.
- 공중화장실 원천파일을 확보해 현재 컬럼·인코딩·갱신일·좌표 제공 여부를 확인한다.

**산출물**은 실연동 검증표, 허용된 범위의 응답 예시, API별 이용 조건표, 데이터 원본 정보다. **완료 조건**은 각 실제 기능의 정상 응답과 대표 실패 상황을 확인하고, 경로를 실제 지도에 그릴 수 있는 것이다. SRS 13절의 10개 항목을 각각 판정한다.

2026년 11월 8일 지역 CSV 적재와 실제 카카오 지도·주소·시설·세 가지 경로 응답을 확인했다. Edge에서 자동차 추천 경로를 그려 확인했다. 전국 원본 파일 확보, 실제 접근점과 앱별 과금 조건은 후속 검증으로 남아 있다. [재개 2단계 검증 기록](검증_FindNearby_재개2공개자료.md)

### 재개 3 추천 정책과 공통 데이터 형식 정리

**선행 조건은 실제 응답 스키마와 기존 코드 구조 확인이다.**

- SRS의 FR·NFR·AT 항목을 구현 위치와 검증 방법에 연결한다. 요구사항과 단계 기록이 다른 부분은 SRS를 기본 기준으로 보완한다.
- 초기 반경을 도보 500m, 대중교통·자동차 2km로 정리하고 반경 확대 순서를 하나의 정책으로 관리한다.
- 시설 좌표와 경로 도착점을 구분하고, 좌표 변환·거리 단위·시간 단위·출처·계산 시점·상태를 공통 형식으로 정의한다.
- 대중교통 도보거리 합계와 세 이동수단의 동률 기준을 정의한다. 경로 대안 선택과 시설 순위가 같은 정책을 사용하도록 한다.
- 조건 변경 후 갱신, 요청 취소·중복 방지, 추천 선택 시 상세 로딩, 검색 제한에 도달했을 때의 응답을 정의한다.
- 기존 모듈을 재사용하면서 화면, 시설 검색, 경로 제공자, 추천 정책, 데이터 저장소의 책임과 의존성을 확인한다.

**산출물**은 요구사항 대응표와 상세 설계다. **완료 조건**은 동일 입력의 순위와 상태 전이가 명확하고, 프런트와 백엔드가 같은 응답 형식·정렬 기준을 사용하는 것이다.

### 재개 4 후보 탐색과 경로 추천 보완

**선행 조건은 재개 3의 추천 정책과 재개 2의 실제 API 확인이다.**

- 초기 후보를 평가한 뒤 유효 경로가 3개 미만이면 미평가 후보, 다음 페이지, 다음 반경 순으로 탐색을 이어간다. 이미 조회·평가한 시설은 식별자와 보정 도착점을 기준으로 재사용한다.
- 탐색 종료 조건을 데이터 소진, 최대 반경, 호출 예산, 전체 제한 시간, 유효한 순위 종료 근거로 구분한다. 결과에 평가 수·반경·중단 이유를 포함한다.
- 유효 경로 3개를 확보한 후에도 위 종료 조건으로 추가 탐색 여부를 판단한다. 다음 후보가 현재 3위보다 우수할 가능성과 데이터 조회 범위를 함께 고려한다.
- 도보의 거리 하한은 실제 사용한 도착점과 API의 도로 연결 보정까지 고려해 성립 여부를 검증한다. 시간 순위에는 별도로 검증된 시간 하한 또는 명시적인 탐색 예산을 적용한다.
- 자동차는 다중 목적지 API의 지원 범위를 판정하고, 10km 밖 후보와 제한에 따른 실패에 단일 목적지 요청을 연결한다. 요약·상세 요청은 같은 도착점과 경로 옵션을 사용한다.
- 추천과 상세 조회의 기준값·계산 시점 차이를 표시하고, 시설 선택 시 필요한 경로 좌표를 가져온다.
- 일시적인 오류는 전체 시간·호출 예산 안에서 제한적으로 재시도한다. 부분 성공, 모든 후보 경로 없음, API 장애, 예산 소진을 구분한다.
- 재시작 후에도 유지되는 서비스 전체 호출 한도와 API별 사용량 집계를 구현한다. 동시 요청의 한도 차감을 일관되게 처리하고 재시도·상세 조회·주소 변환을 집계에 포함한다.

**산출물**은 보완된 검색·추천 기능과 회귀 검증 결과다. **완료 조건**에는 다음 사례를 포함한다.

- 첫 후보 10개에 유효 경로가 2개뿐이고 다음 후보에 경로가 있으면 탐색을 이어가 3개를 반환한다.
- 첫 후보에 유효 경로가 3개 이상 있어도 다음 후보가 우회가 적어 더 우수한 경우, 탐색 예산과 종료 기준에 따라 해당 후보를 평가해 순위에 반영한다.
- 대중교통에서 시간·환승이 같고 전체거리와 도보거리의 순위가 반대이면 도보거리 기준으로 결정한다.
- 도보·대중교통·자동차의 동률은 시설 ID까지 일관되게 처리한다.
- 자동차 후보가 10km 안팎에 섞여 있어도 평가 가능한 후보를 비교하고 실패 원인을 표시한다.
- 동일·매우 가까운 출발지와 도착지를 처리하고, 오래된 응답이 최신 검색 결과를 덮어쓰지 않는다.

2026년 11월 8일 추가 후보 탐색, 중단 사유, 공통 응답 형식과 지속 호출 한도를 구현했다. 자동 테스트 20건과 Edge의 실제 자동차 추천·경로선 및 늦은 응답 처리를 확인했다. 도보 거리 하한에 필요한 도로 연결 보정의 상한은 공개 규격에서 확인할 수 없어 반경과 예산을 기준으로 탐색을 종료한다. [재개 4단계 검증 기록](검증_FindNearby_재개4추천탐색.md)

### 재개 5 실제 시설 데이터와 도착점 보완

**선행 조건은 실제 원천 데이터와 저장·재사용 조건 확인이다. 재개 4와 독립적인 CSV 정제는 병행할 수 있다.**

- 실제 CSV를 소량 적재해 필수값, 중복, 좌표 누락, 주소 변환 실패를 집계하고 지역별 유효 데이터 범위를 확인한다.
- 주소의 표기 차이와 실제 오매칭을 구분한다. 불명확한 행은 검토 대상으로 남기고, 유효 데이터와 별도로 집계한다.
- 검증된 출입구·차량 접근점에 출처와 확인일을 기록한다. 이름이 같거나 350m 이내 후보가 여러 개인 경우에는 매칭 근거를 추가로 확인한다.
- 공공데이터와 검색 API의 중복 시설을 통합하고 동일 시설의 서로 다른 입구를 구분한다. 도착점이 바뀌면 해당 좌표로 경로를 평가한다.
- 일부 데이터만 가져온 경우의 재실행, 기존 레코드 유지·갱신·삭제, 접근점 참조 유지, 실패 시 복구를 검증한다.
- 대표점·출입구·차량 접근점의 차이와 데이터 부족 지역을 화면에 표시한다. 실제 개방 여부·주차 가능 여부는 출처가 제공하는 정보 수준에 맞춰 표현한다.

**산출물**은 실제 시설 데이터, 가져오기 결과, 위치·접근점 표본 검증 기록이다. **완료 조건**은 6단계 기록의 기준에 따라 위치 표본 30곳 이상을 대조하고, 누락·오매칭·중복·재가져오기 처리와 이동수단별 도착점 적용을 확인하는 것이다.

2026-11-08에 공중화장실 91곳과 지하철역 3곳의 출입구 5개를 반영했다. 화장실 30곳을 주소 검색과 대조해 28곳을 확인했고, 좌표 차이가 큰 2곳은 보류했다. 차량은 등록된 접근점의 적용을 테스트했으며, 이번에 확보한 공식 자료 범위에서는 대표 좌표를 사용한다. [재개 5단계 검증 기록](검증_FindNearby_재개5시설데이터.md)

### 재개 7 통합 인수·성능·비용 검증 (기존 8단계)

**선행 조건은 재개 1~6의 기능 완료다.**

1. **7-1 시험표와 호출 예산 확정.** 초기 시험표는 서울·수도권, 지방 대도시, 농어촌, 강·철도 우회 지역의 30개 출발지에 이동수단과 시설 유형을 교차 배정한 90개 조합이다. 이번 실연동은 그중 15개 조합으로 제한한다. [요구사항 대응표](검증_FindNearby_요구사항대응표.md)
2. **7-1 소규모 실호출.** 세 이동수단을 예비 시험해 시설 검색·경로·재시도·자동차 상세에 드는 호출을 구분했다. 실측한 소요량, 앱 쿼터와 개발 서버 일일 한도를 바탕으로 날짜별 시험량을 정한다. 지도 SDK 사용량은 앱 콘솔에서 별도로 확인한다. [개발 한도 설정](../Dev/안내_FindNearby_개발실행.md#실제-api-설정) · [카카오 쿼터](https://developers.kakao.com/docs/ko/getting-started/quota) · [카카오모빌리티 가격](https://developers.kakaomobility.com/price/)
3. **7-2 실제 화면 인수시험.** FR-01~20과 AT-01~12에 시험 근거를 연결한다. Safari와 실제 iOS·Android에서 출발지, GPS 허용·거부, 목록·지도, 상세 경로를 확인하고 화면 읽기 프로그램으로 핵심 흐름을 점검한다. 휴대폰에서 접근 가능한 HTTPS 시험 주소가 필요하면 재개 8의 시험 환경 설정 중 필요한 부분을 앞당긴다. 농어촌의 정상적인 시설·경로 없음, 좌표가 없는 공공자료, 차량 대표점 때문에 생긴 접근 문제, 외부 API 오류를 구분해 기록한다.
4. **7-3 성능·비용 판정과 수정.** 정상 외부 API 조건에서 검색 시작부터 화면에 추천이나 완료 상태가 표시될 때까지 측정해 P95 10초 목표를 평가한다. 결과 개수·평가 수·중단 사유와 자동차 상세 조회 시간을 함께 기록한다. 공급자 실패·한도 소진·통신 중단은 정상 표본과 나눠 집계하며 느린 정상 응답은 포함한다. 중복 요청과 동시 요청은 재현용 응답으로 반복 확인하고, 실제 요청은 시험 예산 안에서 확인한다. 현재 공용 캐시가 없으므로 적중률은 해당 없음으로 기록한다. 사용량 DB는 UTC 일일 한도에 필요한 기록만 남기므로 시험일마다 API별 시도 수·실패율·재시도를 따로 집계한다.

**이번 시험 완료 기준**은 사용자 요청으로 선정한 15개 실연동 조합의 결과와 호출량을 기록하는 것이다. 미통과·미검증 항목은 원인과 재검증 조건을 기록한다. 최소 90개 조합과 기기별 근거는 SRS 전체 인수 기준으로 남는다.

2026-11-08 재개 7-1에서 출발지 30곳의 시험 조합 90개를 구성했고, 도보·대중교통·자동차 추천과 자동차 상세의 실제 외부 호출 36회를 집계했다. 무료 사용 기준으로 기본 한도에 맞춘 30시험일 계획을 마련했다. [재개 7-1 시험표와 호출 예산](검증_FindNearby_재개7-1시험표및호출예산.md)

2026-11-08 재개 7-2에서 로컬 데모 90개와 O01 실제 웹 3개 조합을 확인했다. 같은 집계일에 O02 홍대입구역 도보 조합을 추가했다. 15개로 조정한 실연동 범위에서 4개를 완료했다. [재개 7-2 인수시험 기록](검증_FindNearby_재개7-2화면인수시험.md)

### 재개 8 배포 준비와 시험 운영 (기존 9단계 전반)

**선행 조건은 재개 7의 인수 판정과 호스팅·도메인·운영 예산 결정이다.** 실제 기기 시험용 주소는 인수 기간 중 준비할 수 있다.

1. 프런트 빌드, FastAPI 실행 구성, 공공자료 초기 적재 및 DB 영속 저장 절차를 `Build`에 정리한다. 시험 주소와 운영 도메인, HTTPS, 카카오 JavaScript SDK 도메인, 서버용 비밀키 주입을 설정한다.
2. 로그인 없는 검색 흐름에 공개 요청 제한을 적용하고 운영 기능의 접근을 통제한다. 운영 한도와 공급자 앱의 과금 설정을 대조한다. 배포 산출물·공개 URL·로그에 서버 키나 정확한 사용자 좌표가 포함되는지 점검한다. 자동차 API 이용 조건과 위치정보 보유·삭제 기준, 공공자료 출처·갱신 책임을 정리한다. [이용 조건 확인 기록](검증_FindNearby_재개2공개자료.md)
3. 시험 환경에서 지도·검색·세 가지 경로, 재시작 후 DB·호출량 유지, 한도 소진, 동시 요청, 백업 복원과 이전 버전 복귀를 확인한다. 응답시간·오류율·호출량·자료 기준일에 대한 운영 지표와 알림 기준을 정한다.

**완료 기준**은 시험 주소에서 배포 결과물을 재현하고 인수 핵심 흐름, 한도, 보안과 복구 절차를 검증하는 것이다. 운영 예산과 공개 범위를 확정한다.

2026-11-09 시험 배포 ZIP을 만들고 로컬에서 실제 지도·주소·세 이동수단, HTTPS 연결, 요청 제한과 백업·복원·롤백 모의를 확인했다. 비공개 HTTPS 주소 확보 후 실제 모바일·Safari 시험과 운영 예산·공개 범위 확정을 이어간다. [재개 8단계 시험 배포 기록](검증_FindNearby_재개8시험배포.md)

### 재개 9 공개 전환과 초기 운영 (기존 9단계 후반)

**선행 조건은 시험 배포 통과와 공개 결정이다.**

1. 운영 URL에서 지도·출발지·세 시설 유형과 세 가지 경로를 점검한다. 모바일 HTTPS 위치 권한, 출처 표시, 이용 한도와 장애 안내를 확인한다.
2. 공개 후 정해 둔 관찰 기간 동안 응답시간, 오류율, 호출량·과금, 자료 갱신 상태를 점검한다. 이상이 기준을 넘으면 호출량을 제어하고, 필요하면 공개를 중단하거나 검증한 이전 버전으로 복귀한다.
3. 공개 결과와 운영·복구 절차를 기록한다. 공공 화장실 좌표 확대, 보류한 시설 위치 재검토와 차량 진입점 확보는 지역별 인수 결과를 기준으로 우선순위를 정한다. 개방시간·접근성 필터는 해당 자료가 확보된 뒤 검토한다.

**완료 기준**은 운영 URL에서 핵심 인수 흐름이 통과하고 관찰 기간의 운영 지표와 담당자가 정리된 상태다.
