# FindNearby 추천 정책과 공통 응답 형식

재개 3단계 설계다. 초기 반경과 순위의 기준은 SRS 5절을 따르고, 재개 2단계에서 확인한 카카오 응답을 기존 프런트엔드와 서버 사이의 공통 형식으로 유지한다. 아래의 목표 응답 필드와 동작은 재개 4단계에서 구현한다. [요구사항](REQUIREMENTS_DEFINITION_SRS_v1.0.md), [실연동 검증](검증_FindNearby_재개2공개자료.md), [요구사항 대응표](검증_FindNearby_요구사항대응표.md)

## 검색과 순위

| 이동수단 | 반경 순서 | 시설 순위 기준 |
| --- | --- | --- |
| 도보 `walk` | 500m → 1km → 3km → 5km → 10km → 20km | 이동거리 → 소요시간 → 시설 ID |
| 대중교통 `transit` | 2km → 3km → 5km → 10km → 20km | 총 소요시간 → 환승 횟수 → 도보 구간 거리 합계 → 시설 ID |
| 자동차 `car` | 2km → 3km → 5km → 10km → 20km | 소요시간 → 주행거리 → 시설 ID |

모든 기준은 오름차순이다. 서버는 화면 표시용으로 반올림하기 전의 미터·초 정수값과 시설 ID 문자열의 사전식 순서를 사용하고, 화면은 서버 배열 순서대로 순위를 표시한다. 같은 시설의 복수 경로는 표의 수치 기준을 적용하고, 수치가 모두 같으면 공급자의 반환 순서상 첫 경로를 사용한다. 대중교통의 도보거리는 `kind=walk` 구간의 `distance_m` 합계다. 구조가 유효하고 도보 구간이 없는 경로의 합계는 0m다. 구간 거리나 환승 정보가 누락되면 동률 판정에 필요한 값을 확인할 수 없는 후보로 분류한다.

1. 선택한 출발지와 시설 유형을 기준으로 초기 반경을 조회한다. 편의점·지하철역은 카카오 카테고리, 화장실은 유효한 공공 좌표를 우선 사용하고 카카오 키워드 결과로 보강한다. 페이지와 반경이 겹쳐도 같은 시설 ID는 한 번 평가한다. 출처가 다른 같은 시설의 중복 판정에는 시설명과 좌표를 함께 쓰며, 별도 출입구는 시설 데이터와 분리한다.
2. 시설 대표 좌표로 반경을 판단한다. 정제된 후보를 대표 좌표의 직선거리와 ID로 정렬하고 처음 10개까지 경로를 평가한다. 경로에 넘기는 도착점은 검증된 모드별 접근점이 있으면 그 좌표를, 그 외에는 시설 대표 좌표를 사용한다.
3. 유효 경로가 3개 미만이면 미평가 후보 → 현재 반경의 다음 페이지 → 다음 반경 순으로 이어간다. 3개를 확보한 뒤에도 더 높은 순위가 나올 수 있고 예산이 남으면 같은 순서로 평가한다. 페이지 종료는 공급자 `is_end`와 지원 페이지 범위로 판단한다. 최종 결과는 평가가 완료된 후보 가운데 상위 3개까지 반환한다.
4. 도보는 보정된 출발·도착 좌표와 도로 연결 오차까지 고려해 검증한 하한이 남은 후보 전체에 적용되고, 그 하한이 현재 3위 거리보다 **클 때만** 순위 근거로 탐색을 종료한다. 같으면 시간과 ID로 순위가 바뀔 수 있다. 대중교통과 자동차의 시간 순위는 검증된 시간 하한이 생길 때까지 탐색 범위·예산으로 종료를 판단한다.
5. 자동차 다중 목적지는 실제 도착 좌표가 10km 안에 있는 후보를 최대 30개 단위로 요약 평가한다. 범위 밖 후보나 다중 목적지 응답에서 누락된 후보는 예산이 허용할 때 단건 경로로 평가한다. 요약과 상세 요청은 같은 도착 좌표와 공통 경로 옵션을 사용한다. 공급자 호출 한도나 인증 오류가 확인되면 해당 공급자로의 추가 호출을 중단한다.

화면에는 **검색된 시설 중 추천 경로 상위 3개**와 함께 실제 조회한 반경과 제한 사유를 표시한다. 20km는 시설 검색 상한이고, 자동차 다중 목적지의 10km는 경로 API 제약이다. [카카오 장소 검색 규격](https://developers.kakao.com/docs/ko/kakaomap/rest-api), [자동차 다중 목적지 규격](https://developers.kakaomobility.com/guide/navi-api/destinations)

## 프런트엔드와 서버의 공통 형식

기존 `POST /api/recommend`와 `POST /api/route`를 사용한다. 프런트엔드의 `Contracts.ts`와 서버의 `Models.py`에 같은 필드와 값을 반영한다. 기존 필드는 유지하고, 아래에서 추가로 표시한 필드를 서버와 화면에 함께 적용한다. [서버 모델](../Dev/server/Models.py), [화면 타입](../Dev/src/Contracts.ts), [API 진입점](../Dev/server/FindNearbyApi.py)

| 항목 | 공통 정의 |
| --- | --- |
| 요청 | `origin`, 시설 유형 `kind`, 이동수단 `mode`, 데모 여부 `demo`. 상세 요청에는 `destination`을 포함 |
| 좌표 | WGS84 숫자 객체 `{lat, lng}`. 서버 입력에서 유한값과 지원 범위를 검증하고, 카카오의 `x=lng`, `y=lat` 및 배열 좌표는 공급자 연결부에서 변환 |
| 시설 | `id`, `name`, `address`, `kind`, 대표 `coordinates`, `source`, `hours`, `updated`. 출처는 `public`, `kakao`, `demo`. 주소·개방시간·기준일의 빈 값은 화면에서 생략하거나 미제공으로 표시 |
| 추천 | `facility`, `access` 또는 `null`, 순위에 사용한 `route`. 추가 필드 `destination`은 서버가 경로 계산에 사용한 실제 요청 좌표이며 상세 요청에도 그대로 사용. 시설 마커는 대표 좌표에 표시 |
| 경로 | `distance_m`, `duration_s`, `transfers`, `fare_won`, `calculated_at`, `segments`. 거리와 시간은 0 이상의 미터·초 정수, 요금 미제공은 `null`, 계산 시각은 UTC 기준 ISO 8601 문자열 |
| 경로 추가 필드 | `source`는 `kakao_maps`, `kakao_mobility`, `demo`. `geometry`는 `summary` 또는 `polyline`. `walking_distance_m`은 도보·대중교통의 도보 구간 합계이며 자동차는 `null` |
| 경로 구간 | `kind`는 `walk`, `bus`, `subway`, `car`. 거리·시간·순서가 있는 `path`와 노선 `lines`, 정류장 `stops`를 구간 단위로 유지 |
| 검색 결과 | `recommendations`는 순위대로 0~3개. `radius_m`은 마지막으로 결과를 확보한 반경이며 조회 전 한도에 걸렸으면 0. `demo`는 요청에 사용한 데이터 모드 |
| 검색 집계 | 추가 필드 `matched`는 중복 제거된 유효 시설 수. `evaluated`는 최종 경로 결과가 나온 고유 후보 수로 성공·경로 없음·실패의 합계. `unavailable`은 경로 없음, `failed`는 공급자·응답 실패 수. 미평가 후보와 재시도 횟수는 `evaluated`에서 제외 |
| 검색 중단 | 추가 필드 `stop_reason`은 `exhausted`, `radius_limit`, `rank_bound`, `call_budget`, `rate_limited`, `deadline`, `provider_error` 중 하나. 아래 표의 조건에 따라 지정 |

`geometry=summary`는 거리와 시간이 있는 자동차 요약이며 `segments`는 빈 배열이다. `polyline`은 적어도 한 구간에 지도에 그릴 수 있는 좌표가 있다. 구간별로 좌표가 있는 부분만 그려 서로 떨어진 구간 사이에 선이 생기지 않도록 한다. 자동차 상세 소요시간이나 거리가 요약과 달라지면 추천 카드는 기존 순위와 요약을 유지하고, 선택 상세 영역에는 상세 값과 각 조회 시각을 구분해 표시한다.

출발·도착 좌표가 같거나 공급자가 근접 지점에서 유효 경로가 없다고 반환하면, 경로 없음으로 처리하고 해당 후보를 제외한다. 사용자가 선택한 시설 상세에서 같은 상황이 확인되면 사유를 안내하고 다른 시설을 선택할 수 있게 한다.

## 중단과 화면 상태

| 종료 코드 | 서버의 판단 | 화면에 전달할 정보 |
| --- | --- | --- |
| `exhausted` | 공급자의 남은 탐색 범위에 후보가 없음을 확인하고 조회한 후보를 모두 처리 | 결과가 0개면 시설 없음 또는 유효 경로 없음, 1~2개면 해당 개수 표시 |
| `radius_limit` | 20km 범위의 마지막 후보까지 처리했고 추가 탐색에 20km를 넘는 조회가 필요 | 20km 이내 평가 결과라는 범위 표시 |
| `rank_bound` | 남은 후보가 기존 상위 3개 순위를 바꿀 수 없다는 검증된 근거 확보 | 평가 범위와 추천 순위 표시 |
| `call_budget`, `rate_limited`, `deadline` | 호출 예산, 공급자 제한, 검색 시간 중 하나로 다음 요청을 시작할 수 없음 | 확보한 결과와 제한 사유를 함께 표시. 결과 0개도 검색 완료로 판단하지 않음 |
| `provider_error` | 오류 때문에 일부 검색 범위나 후보를 평가할 수 없음 | 유효 결과를 유지하고 부분 오류 안내. 결과를 제공할 수 없는 공급자 장애는 기존 HTTP 오류와 `detail` 반환 |

요청 자체가 잘못되면 기존 입력 오류를 반환한다. 단건 상세의 경로 없음은 기존 HTTP 404로 구분한다. 검색 중 후보 단위의 경로 없음은 실패와 별도로 집계한다. 정상 완료 전에 중단되면 다음 조회를 막은 원인을 반환하며, 호출 전에 제한된 후보는 미평가로 남긴다. 분당·일일 한도와 검색별 호출·시간 예산을 확인하며, 시도와 재시도 모두 사용량에 포함한다. 일시 오류는 남은 예산이 있을 때 최대 한 번 재시도하고, 인증 오류·429·정상적인 경로 없음은 즉시 분기한다. [개발 서버 한도](../Dev/안내_FindNearby_개발실행.md#실제-api-설정)

| 사용자 동작 | 화면 상태와 요청 |
| --- | --- |
| 최초 추천 실행 | 현재 조건으로 요청하고 검색 중 상태 표시 |
| 출발지·시설·이동수단 변경 | 최초 검색 이후 짧은 입력 대기 뒤 다시 검색. 이전 검색과 상세 요청은 취소하고 화면에서 제거 |
| 최신 응답 수신 | 요청 실행마다 구분되는 번호가 현재 실행 번호와 같을 때만 반영. 같은 조건의 요청이 진행 중이면 중복 전송 방지. A→B→A에서도 이전 A 응답은 폐기 |
| 추천 응답 반영 | 최대 3개 마커를 표시하고 기본 선택은 1위 |
| 시설 선택 | 경로 좌표가 있으면 바로 강조. 요약만 있으면 해당 시설의 `destination`으로 상세 로딩을 시작 |
| 상세 조회 실패 | 선택과 추천 목록을 유지하고 실패 이유와 다시 조회 버튼 표시. 다른 시설로 바뀌면 이전 상세 응답 폐기 |

브라우저 요청을 취소하면 오래된 응답의 표시를 막을 수 있다. 이미 시작한 공급자 요청은 호출 예산에 남으므로 서버는 다음 호출 전 예산과 종료 시간을 확인한다. 공급자 검색·경로 응답은 현재 추천 요청이나 표시 세션에서 사용하며, 공용 응답 캐시와 좌표 DB는 재개 2단계에서 확인한 이용 조건을 적용한다. [실연동 및 이용 조건](검증_FindNearby_재개2공개자료.md)

## 책임과 현재 기준본 확인

| 책임 | 기존 위치와 적용 방향 |
| --- | --- |
| 화면 상태와 지도 | `App.tsx`는 선택·요청 상태, `MapView.tsx`는 마커와 구간 그리기를 담당 |
| 입력과 응답 | `FindNearbyApi.py`와 `Models.py`가 HTTP 입력·오류·직렬화를 담당하고, `Contracts.ts`가 화면 타입을 정의 |
| 후보와 순위 | `RecommendationService.py`가 반경·페이지·평가 순서·종료 정책을 한 곳에서 관리. 순위는 기존 `Route.rank_key`와 시설 ID 사용 |
| 공급자와 사용량 | `KakaoProvider.py`가 외부 요청과 응답 변환을 담당. 로컬 한도를 적용하는 기존 `CallBudget`은 재개 4단계에서 재시작 후에도 유지되는 집계로 보완 |
| 시설 데이터 | `FacilityStore.py`가 공공 좌표와 접근점 조회를 담당. CSV 정제와 실제 접근점 정합성은 재개 5단계에서 확인 |

기준본은 초기 반경, 이동수단별 동률 규칙, 자동차 상세 지연 로딩을 구현하고 있다. 현재는 시설 수를 기준으로 최대 10개를 선택한 뒤 경로를 평가하고, 그 이후 남은 후보·페이지로 돌아가지 않는다. 브라우저는 조건 키와 취소 신호를 사용하며, 실행 번호를 통한 동일 조건 재진입 처리와 중단 사유 필드는 목표 설계에 포함했다.

FastAPI가 생성한 OpenAPI와 TypeScript에서 좌표·장소·시설·경로 구간·경로·추천 항목·추천 응답·추천 요청의 8개 구조를 대조했다. 필드 이름, 값의 종류와 배열·`null` 구조가 일치했다. 기존 Python 자동 테스트 10건과 TypeScript 타입 검사가 통과했다. 이 결과는 현재 기준본의 확인 기록이며 추가 필드와 검색 확장 정책은 재개 4단계 인수 시험의 기준이다.
